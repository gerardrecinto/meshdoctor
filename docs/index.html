Catch the Istio 503 before you apply it

meshdoctor reads your Istio and Kubernetes YAML and flags the mistakes that become outages: canary weights that do not add up, subsets that do not exist, mTLS mismatches, no outlier detection.

go run github.com/gerardrecinto/meshdoctor/cmd/meshdoctor@latest deploy/

What it checks

Eleven rules. Each one is a mistake that either fails at apply time or shows up later as a 503.

The rest of the kit

The linter is the center. Around it is what a production mesh team also runs.

Go

meshdoctor CLI and WASM

Text, JSON and GitHub annotation output. Exit code 1 on errors, --strict for warnings. Table-driven tests per rule.

Java 21

checkout service

The mesh workload. Version from env, a failure rate for outlier tests, readiness that flips on SIGTERM. JUnit tests, non-root image.

Python

SLO burn-rate alerts

Turns an availability SLO into four multi-window Prometheus alerts on Istio's own request metric. Worked budget math in the tests.

Jenkins

Pipeline and shared library

Parallel Go, Python and Java tests, a meshGate library step, Terraform validate, and the e2e on main.

Terraform · AWS

EKS with Istio

VPC, EKS with IMDSv2 only and a CIDR-restricted API, Istio base, istiod and an NLB ingress through Helm. Validated, not applied.

Runbooks

503 flags, rollback, no sidecar

Short pages written for the person on call: which flag means config, endpoints, TLS or the service.

Limits

Lint checks only the files you give it; a rule that needs another resource says so when that resource is missing. The Terraform is validated with terraform validate and was not applied to an AWS account. The Jenkinsfile was syntax-checked by a Jenkins controller but not run on a build agent. The e2e is one namespace and two replicas: it shows behavior, not capacity.
